The gap PaSO fills

Two worlds that need to meet

Wallets have the cryptography. Payments regulation demands proof. OpenID4VP leaves a deliberate gap between them. PaSO closes it — in a focused, interoperable way.

🔐

Wallets have the cryptography

A device-bound key, unlocked by PIN or biometric, capable of signing a presentation — exactly the primitives that Strong Customer Authentication needs.

⚖️

Regulation needs more than a signature

What did the user actually see? What did they consent to? Can the proof be independently re-checked later? Will every wallet behave consistently?

🧩

OpenID4VP leaves the space open

transaction_data is the hook for dynamic linking, but its meaning, display, and resulting proof are intentionally out of scope. Without agreement, interoperability collapses.

What PaSO is

A trust and proof framework, layered on top of OpenID

PaSO is a modular set of standards on top of OpenID4VCI and OpenID4VP. A small core defines the shared concepts; additional modules add proof packaging, rendering, metadata, logging, and trust.

Four roles

In payments, the party that asks isn't always the party that authorizes

PaSO names four roles. Keeping them distinct is one of its defining ideas.

Attestation Provider

Issues PaSO credentials into the wallet. The credential issuer in OpenID4VCI terms.

Wallet

Stores PaSO credentials, processes transaction data, displays it to the user, and produces the proof.

Relying Party

Sends the signed presentation request with transaction data and receives the wallet's presentation. The verifier in OpenID4VP terms.

Authorizing Party

Independently verifies the proof and authorizes the transaction. Holds trust relationships with the attestation provider and the relying party.

The split between Relying Party and Authorizing Party cleanly models the difference between, say, a merchant-side service that collects the user's consent and the bank that actually verifies and acts on it.

Two flows

First-party and third-party

Switch between the two arrangements PaSO supports. In both, presentation requests are signed and wallets reject unsigned PaSO requests.

One party plays attestation provider, relying party, and authorizing party at once. The wallet presents a credential back to the party that issued it — the bank authenticates its own customer directly.

Regulatory significance. Under eIDAS 2.0 Article 5f(2), private relying parties already obliged to use strong user authentication must also accept European Digital Identity Wallets. Because PSPs already perform SCA under PSD2, this puts banks and PSPs squarely in scope by late 2027. The first-party flow is the direct technical expression of this duty.

Relying party (merchant or merchant-side service) is separate from the authorizing party (bank or scheme). The relying party collects consent and forwards an unmodified proof package onward.

Payment schemes carry the package. The scheme provides the rails: it transports the proof package from the merchant side to the issuing bank acting as Authorizing Party, and specifies how the bank evaluates the evidence.
The proof

Independently re-verifiable. Replayable. Tied to what the user actually saw.

PaSO's holder binding proof captures not just that the user signed, but what they were shown and how they authenticated.

jti

Single-use authentication code

A fresh, unique, high-entropy identifier per presentation. In an SCA context, this is the authentication code.

amr

Authentication methods

Explicit values distinguish strong from weaker biometrics. In payments, factors must span at least two independent categories.

transaction_data_hash

Dynamic linking

A hash of the exact transaction data the user consented to. Any change to amount or payee invalidates the proof.

request_integrity

Tamper-evident request

An integrity value over the signed request the wallet received — the request the user acted on is part of the evidence.

metadata_integrity

Signed display metadata

An integrity value over the signed credential metadata used to display the transaction. The wallet did not render arbitrary issuer UI.

locale + wallet

Exactly what was shown

The locale the user actually saw and the wallet's version — so the displayed text can be precisely reconstructed.

Proof package. In a third-party flow, the relying party forwards an unmodified package — the original signed request plus the wallet's presentation — to the authorizing party, which re-verifies the request signature, credential validity, holder binding proof, SCA response claims, and conformance to the applicable rulebook. PaSO defines a standard ingestion endpoint and an optional signed-and-encrypted envelope for this hand-off.
Faithful display

"The user consented" → "The user demonstrably saw exactly these details"

Informed consent depends entirely on what the user sees. PaSO View defines how a wallet renders transaction data generically, driven only by signed metadata.

Generic, metadata-driven

Each displayable claim carries a value type (currency, date, image, frequency, URL, inline-formatted text, template). The wallet knows how to render each one.

Mandatory and faithful

Everything designated for display must be shown before the user can confirm. Labels and hints may not be used to obscure consent-relevant information.

Deterministic locale

The wallet selects the display locale by defined matching rules and records the locale used in the proof.

Choice without coupling

When a request offers several credentials or entries, the wallet presents them as independent choices. A consistency property ensures they are genuinely independent.

Two integration paths

Static or dynamic — the choice that decides whether a wallet scales

A wallet provider can hard-code every transaction type, or it can render any type from signed metadata. The second is what makes adoption viable.

Static path

Hard-coded transaction types

  • ✅ Simple for a small, fixed set of types
  • ✅ Full control over look and feel
  • ❌ Every new type needs a code change and a wallet release
  • ❌ A wallet can only transact a type it has already shipped
  • ❌ Cannot scale to types defined by many different organisations
Dynamic path

Metadata-driven rendering

  • ✅ Signed metadata describes claims, display rules, labels per locale
  • ✅ One generic renderer handles every type — present and future
  • ✅ A new type is introduced by publishing metadata and a rulebook
  • ✅ The wallet needs no update — safe because metadata is signed
  • ✅ Precondition for using a wallet as a general bank SCA mechanism
Today's banking apps already show transaction-bound consent for far more than payments — logging in, changing limits, adding payees, security changes. Under the static path, every interaction across every bank would need bespoke wallet UI. Under the dynamic path, banks publish signed metadata and the wallet renders it generically. A wallet becomes a universal, transaction-aware consent surface for financial interactions.
Versioned type identifiers

Govern, don't hard-code

Every PaSO transaction data type is named by a versioned URN. The structure of a published type is immutable — any change requires a new version. A relying party can offer a newer type first and an older type as a fallback. 

urn:paso:sca:<domain>:<suffix>:<version>
domain — owner of the type, or global
suffix — name of the type, e.g. payment
version — version number; semantics are immutable per version
Regulatory mapping

How PaSO mechanisms map onto SCA requirements

PaSO does not by itself make any deployment compliant — compliance depends on the full implementation, credential and rulebook design, and assessment by the responsible parties. The mapping below shows where PaSO contributes.

Two independent SCA factors PSD2 Art. 4(30), 97 · SCA-RTS Arts. 6–9 · EBA Opinion Device-bound key (possession) released by PIN/biometric; amr records factor categories and biometric strength
Single-use, unforgeable authentication code SCA-RTS Art. 4 Unique per-presentation identifier in a device-key signature; replay checking at the authorizing party
Dynamic linking to amount and payee PSD2 Art. 97(2) · SCA-RTS Art. 5 Signed hash of the exact transaction data; any change invalidates the proof; re-checked by the authorizing party
Integrity of the authenticated request SCA-RTS Art. 5(1) Signed presentation request plus a recorded request-integrity value
Informed consent / faithful display PSD2 · EBA Opinion Generic metadata-driven rendering; mandatory display before confirmation; recorded display locale
Confidentiality/integrity of credentials and data SCA-RTS Arts. 22–27 Keys confined to secure hardware; signed-and-encrypted proof package; signed credential metadata
Provider's burden of proof in disputes PSD2 Arts. 72, 97 Re-verifiable proof package and replayable wallet-side transaction log
TS12 → PaSO

What changed

PaSO builds on TS12, the technical specification for performing PSD2 Strong Customer Authentication with a wallet, developed within the Large Scale Pilots for the European Digital Identity Wallet to define how OpenID4VP can carry SCA and dynamic linking. PaSO keeps that foundation — OpenID4VP, dynamic linking, and a cryptographic SCA proof — and extends it with the verification, trust, rendering, and governance machinery a real deployment needs.

AreaTS12PaSO
Roles Single verifier; what happens after it receives the presentation is out of scope Distinct Relying Party (collects consent) and Authorizing Party (verifies & settles) — matches real payment topology
Verification "The Relying Party shall verify the presentation" — no procedure, packet, or transport Defined proof package, step-by-step verification procedure, and HTTP ingestion endpoint — independently re-verifiable by the liable party
Metadata trust Transaction types in unsigned VC type metadata; integrity hashes optional Signed credential metadata, issuer-bound, re-verified on every use — admissible as evidence
Rendering Four fixed transaction schemas the wallet must hard-code Generic metadata-driven rendering via reusable value types — new types need no wallet update; the precondition for broad bank adoption
Proof contents jti, amr, transaction-data hash Adds request_integrity, metadata_integrity, display_locale, wallet_instance_version — records what the user saw, not just that they signed
Auth factors Bespoke amr taxonomy IANA RFC 8176 values + checkable bio_strong / bio_weak criteria — interoperable and policy-verifiable
Credential formats SD-JWT VC only SD-JWT VC and mdoc — both mandatory EUDI formats
Multiple credentials Combined presentations mentioned, mechanics undefined Advanced profile with formal transposability + versioned fallback — honest consent, safe upgrades
Audit log List of fields to record Retains request, response, metadata & resolved resources for exact replay — supports the PSD2 burden of proof
Governance One "SCA Attestation Rulebook" concept Split Credential vs Transaction Data Type rulebooks, versioned URN identifiers, generic Mandate type (e-mandates, delegation, agentic commerce)
The bottom line. PaSO turns TS12's foundation into a specification complete enough to deploy — adding the verification, trust, rendering, and governance pieces that real codebases, bank integrations, and settlement paths depend on.
