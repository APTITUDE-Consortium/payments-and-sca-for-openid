    Changelog

    This page lists the changes between published drafts of PaSO. For each draft, it first tells each role what to change in an implementation of the previous draft, then lists the changes document by document.

    Every item carries one tag:

    • Breaking: an implementation of the role that conformed to the previous draft no longer conforms.
    • New: an optional or additive capability.
    • Clarified: a resolved ambiguity or restatement; the intended behaviour is unchanged.

    Section numbers refer to the current draft.

    draft-3 (changes since draft-2)

    Draft-3 is compared with the published draft-2. Changes made and then superseded during the work on draft-3 are not listed; each item describes the draft-3 text.

    What to change

    Wallet

    • Breaking Report in display_locale the locale tag of the rendered entries, or default; it is no longer the priority-list locale. In static rendering, report the selected language tag of the rulebook (Core §6.1, §7.2).
    • Breaking Always include metadata_integrity. Where ad-hoc metadata is used, it identifies the signed credential metadata JWT that authorised the Relying Party (Core §6.1).
    • Breaking Implement the new locale selection: one locale or the default entries for the whole consent screen. If neither is available, the entry is not compatible (View §4, Core §7.2).
    • Breaking Render labels as plain text. Drop display_type, mini_markdown and template:* (View §2, §3).
    • Breaking Accept only PNG and JPEG images, and send Accept: image/png, image/jpeg (View §3).
    • Breaking Treat an entry with more than 10 displayed claim values as not compatible (View §2).
    • Breaking Render a type whose rulebook has a Static Presentation section, such as Payment, only statically, with the rulebook's strings, and use no display data from the credential metadata, including its security_hint. If you do not implement that exact type and version, or the entry carries ad-hoc metadata, the entry is not compatible. Select the language by Lookup among the rulebook's languages, fall back to its fallback language, and report the selected tag in display_locale, never default. This replaces the draft-2 permission for a dedicated UI (View §5, Payment §3). Replay of a static presentation must reproduce your Wallet version's presentation (Log §5).
    • Breaking Stop accepting issuer-signed ad-hoc metadata JWTs. Accept a plain metadata object only from a Relying Party listed in adhoc_metadata_clients, only for types the signed credential metadata does not list, and only after the checks of Metadata §5.3 (Metadata §5).
    • Breaking Reject a request that would let the user present more than one PaSO Credential: more than one PaSO credential query per alternative, an optional PaSO credential set, or multiple set to true (Core §7.3, §7.4.1).
    • Breaking When locale selection fails or no encryption key is available, treat the entry as not compatible and fall back to the next entry, instead of excluding the credential (Core §7.5).
    • Breaking For types that reference the Default risk profile, include an amr envelope; the profile now has eight required signals (Default).
    • New In the simple profile, let the user choose when several credentials match (Core §7.3).
    • Clarified Apply rulebook risk signal profiles, enumerations and encryption requirements only for rulebooks you implement; otherwise follow the signed credential metadata (Core §5.5, Risk Signals §4.1, §7.2).
    • Clarified Compute transaction_data_hash over the entry's base64url string as received, with sha-256 unless the rulebook names another algorithm (Core §6.1).
    • Clarified amr no longer has to cover two categories of authentication elements; it does not establish SCA (Core §4.2, Registry).
    • Clarified Display metadata for SD-JWT VC credentials is now defined in Metadata §9; SVG resources are gone (Metadata §9).

    Relying Party

    • Breaking Build requests that allow exactly one PaSO Credential: every alternative contains exactly one PaSO-referenced credential query, the PaSO credential set is not optional, and no such query sets multiple to true (Core §7.3, §7.4.1).
    • Breaking Stop sending issuer-signed ad-hoc metadata JWTs. To supply ad-hoc metadata, send a plain metadata object; you must be listed in adhoc_metadata_clients, the type must not be published in the signed credential metadata, and its rulebook must not have a Static Presentation section, as Payment's does. The object must follow the label and locale rules of Metadata §3.3 (Metadata §5).
    • Breaking Keep every entry within 10 displayed claim values, and use only PNG or JPEG images (View §2, §3).
    • Breaking Build a Payment payload with exactly the claims of the rulebook, without additional claims (Payment §1).
    • Breaking The Generic and Mandate transaction data types no longer exist. Use ad-hoc metadata or a rulebook of your own (Metadata §5).
    • Breaking If you forward proof packages through the proposed endpoint, send a signed JWT (typ paso-proof-package+jwt, your chain in x5c), and preferably wrap it in a JWE. Plain JSON is no longer accepted. A payment scheme or rulebook may define its own forwarding mechanism instead (Verify §4).
    • New A type you use only with ad-hoc metadata needs no rulebook, and its ad-hoc metadata may carry risk signal configuration (Core §5.1, Risk Signals §4.1).
    • Clarified Keep ad-hoc metadata consistent with any rulebook for its type (Core §5.5).
    • Clarified In versioned requests, a newer entry that fails locale selection or lacks an encryption key now falls back to the older entry (Core §7.5).

    Attestation Provider

    • Breaking Publish ui_labels for every transaction data type rendered dynamically (Metadata §3, §3.2).
    • Breaking List a type whose rulebook has a Static Presentation section, such as Payment, as an empty object in transaction_data_types, without claims or ui_labels. A Wallet that does not implement the rulebook then treats the entry as not compatible (Metadata §3, View §5.1).
    • Breaking A Payment payload contains exactly the claims of the rulebook. You can no longer add internal claims for Payment (Payment §1).
    • Breaking Give every display and ui_labels array of a type the same set of locales, with a default entry in all or none of them. Do not use default as a locale value. Declare at most 10 claims with a display array (Metadata §3.3).
    • Breaking Remove display_type, mini_markdown and template:* from metadata, and SVG templates and images from display resources (View §2, §3).
    • Breaking Issuer-signed ad-hoc metadata JWTs are no longer accepted. Authorise Relying Parties through adhoc_metadata_clients in the signed credential metadata instead (Metadata §5.2).
    • New transaction_data_types may be empty or omit types. Types you do not publish are reserved for the Relying Parties you authorise (Metadata §3, §5.2).
    • Clarified Keep the signed credential metadata consistent with the rulebook of each published type (Core §5.5).
    • Clarified For SD-JWT VC credentials, integrity-verified Type Metadata may be used for display (Metadata §9).

    Authorizing Party

    • Breaking Require exactly one PaSO presentation in the vp_token. Find the matched entry by the presentation's credential query and the hash, without requiring it to be the first-match entry. Accept sha-256, or the algorithm the rulebook names (Verify §3).
    • Breaking Check display_locale against the rendering mode, which follows from the type. If the rulebook has a Static Presentation section, the entry was rendered statically: check that it carries no ad-hoc metadata and that display_locale is one of the rulebook's language tags. Otherwise it is a tag for which every display and ui_labels array has an entry, or default if every array has a default entry. Always check metadata_integrity (Verify §3).
    • Breaking Verify ad-hoc metadata: the client is listed in adhoc_metadata_clients, the type is not published, and the object conforms. For types used only with ad-hoc metadata, check the payload against that metadata (Verify §3).
    • Breaking Do not treat amr as evidence of SCA. SCA rests on holder binding, and the amr check is removed. Where the Default risk profile applies, an amr envelope is now required (Core §4.2, Verify §3, Default).
    • Breaking If you expose the proposed endpoint, accept only a signed JWT or a JWE containing one. Verify the signature, typ and certificate chain, and respond 401 on failure (Verify §4).
    • Clarified Keep applying the rulebook's risk signal profiles, enumerations and encryption requirements when verifying, as in draft-2, even where the Wallet does not implement the rulebook and follows the signed credential metadata (Risk Signals §4.1, §7.2).
    • Clarified transaction_data_hash is computed over the entry's base64url string as received (Core §6.1).

    Rulebook authors

    • Breaking The Credential Rulebook of a PaSO Credential used for Strong Customer Authentication must specify the holder binding and user authentication requirements by which its presentations meet PSD2 Article 97 (Core §4.2).
    • Breaking The Generic and Mandate rulebooks are removed. Types that relied on them need their own rulebook or ad-hoc metadata (Core §5.1).
    • New A rulebook may include a Static Presentation section, which becomes part of the type's immutable semantic structure. It defines what is shown, the meaning of the actions, and the strings in each of its languages, with a fallback language and an optional security hint. The type is then always rendered statically. The Payment rulebook is an example (Core §5.3, Payment §3).
    • New A rulebook may name a hash algorithm other than sha-256 for transaction_data_hash (Core §6.1).
    • Clarified Obligations are stated by role. Wallets build rulebooks in and do not fetch them at runtime, and a type used only with ad-hoc metadata needs no rulebook (Core §5.1, §5.5).

    Changes by document

    Introduction

    • Clarified The overview presents two rendering modes, determined by the type: static rendering from the rulebook for types whose rulebook has a Static Presentation section, and dynamic rendering, which every Wallet supports, for all others (Introduction §6).
    • Clarified Strong Customer Authentication is attributed to holder binding, not to the amr claim (Introduction §4.1, §7 and §9).
    • Clarified Generic transaction types, such as login or limit changes, are served by ad-hoc metadata instead of a generic rulebook (Introduction §6.2, §6.3).
    • Clarified The proof package hand-off uses a proposed endpoint with a signed, optionally encrypted envelope, and a payment scheme may define its own (Introduction §4.2 and §7.2).

    PaSO Core

    • Breaking display_locale reports the locale tag of the rendered metadata entries, or the string default when the default entries were rendered. In static rendering it is the selected language tag of the rulebook and never default (Core §6.1).
    • Breaking The Wallet renders one consent screen from a single locale or entirely from default entries, and display_locale reports that selection; it is no longer the priority-list locale (Core §7.2).
    • Breaking The Credential Rulebook of a PaSO Credential used for Strong Customer Authentication shall specify the holder binding and user authentication requirements by which its presentations meet PSD2 Article 97 (Core §4.2).
    • Breaking A presentation carries exactly one PaSO Credential. The credential query identifiers referenced by PaSO-targeted entries form a single slot, the PaSO slot. Every alternative of its credential set contains exactly one of them, and that set is not optional. Without credential_sets, the PaSO entries reference exactly one credential query. No such query sets multiple to true. A Wallet rejects a request that breaks these rules (Core §7.3, §7.4.1).
    • Breaking Failures have one of three consequences: rejecting the request, excluding the credential, or making the entry not compatible with the credential. A locale-selection failure and a missing encryption key are now entry-level, so the Wallet falls back to the next entry instead of excluding the credential (Core §7.5).
    • New A Transaction Data Type Rulebook may include a Static Presentation section, which defines the static presentation and its strings per language. A type with such a section is always rendered statically; its entry is not compatible if the Wallet does not implement the rulebook or the entry carries ad-hoc metadata. The section is part of the immutable semantic structure of the type (Core §5.3, §7.5).
    • New A type used only with ad-hoc metadata needs no rulebook (Core §5.1).
    • New In the simple profile, several credentials may match the credential query; the user selects one, and the display follows the selection. The simple profile's boundary is stated exactly, and every other PaSO request is in the advanced profile (Core §7.3, §7.4).
    • Clarified Strong Customer Authentication is established by holder binding as required by the Credential Rulebook. amr is an ordinary risk signal: its presence does not establish SCA and its absence does not negate it (Core §4.2, §6.1).
    • Clarified metadata_integrity is always present. For a type rendered statically, it identifies the signed credential metadata JWT that lists the type. Where ad-hoc metadata is used, it identifies the signed credential metadata JWT that authorised the Relying Party (Core §6.1).
    • Clarified transaction_data_hash is computed over the base64url string of the entry exactly as received, without decoding. transaction_data_hash_alg is sha-256 unless the rulebook names another algorithm. These claims are PaSO's representation of transaction data under OpenID4VP §8.4; PaSO does not use transaction_data_hashes (Core §6.1).
    • Clarified Rulebook obligations are stated by role. A Wallet applies the rulebooks it has built in and otherwise relies on the signed credential metadata, which the Attestation Provider keeps consistent with the rulebook (Core §5.5).
    • Clarified Entry compatibility is defined once for both profiles, including when a payload conforms (Core §7.5).

    PaSO View

    • Breaking Labels are plain text. The display_type parameter and the value types mini_markdown and template:* are removed (View §2, §3).
    • Breaking A transaction_data entry may contain at most 10 displayed claim values; otherwise it is not compatible. This replaces the Wallet-defined bound of at least 200 rendered items (View §2).
    • Breaking Images must be PNG or JPEG. SVG is no longer supported, and the Wallet sends Accept: image/png, image/jpeg (View §3).
    • Breaking Locale selection is redefined. The available tags are the locales present in every considered array. The Wallet applies RFC 4647 Lookup for each locale of its priority list, then falls back to the default entries; if neither succeeds, the entry is not compatible (View §4).
    • Breaking Static rendering replaces the draft-2 permission for a dedicated UI. A type whose rulebook has a Static Presentation section is always rendered statically, from the rulebook alone: the Wallet uses the rulebook's strings, in a language selected by Lookup among the rulebook's languages with its fallback language, and no display data from the credential metadata, including security_hint. If the Wallet does not implement that exact type and version, or the entry carries ad-hoc metadata, the entry is not compatible. No party chooses the mode (View §5).
    • Clarified View applies to both the simple and the advanced profile and no longer requires the advanced profile (View §1.1).
    • Clarified Security Considerations move to §6 (new §6.5 on the claim-value limit), References to §7, and Annex A.1 adds locale-selection examples (View).

    Metadata Module

    • Breaking The issuer-signed ad-hoc metadata JWT (adhoc-transaction-metadata+jwt) is removed. Ad-hoc metadata is now a plain metadata object in the transaction_data entry. Only a Relying Party listed in adhoc_metadata_clients may supply it, its authority rests on the signature of the Authorization Request, and it is allowed only for types the signed credential metadata does not list and whose rulebook, where the Wallet implements it, has no Static Presentation section (Metadata §5).
    • Breaking ui_labels is required for every transaction data type rendered dynamically. A type whose rulebook has a Static Presentation section is listed as an empty object, without claims or ui_labels (Metadata §3, §3.2).
    • Breaking All display and ui_labels arrays of a type carry the same set of locales, and either all or none have a default entry. An array has no duplicate locales and at most one default entry. The locale value default is reserved. At most 10 claims may have a display array (Metadata §3.3).
    • New adhoc_metadata_clients lists the Relying Parties authorised to supply ad-hoc metadata (Metadata §5.2).
    • New transaction_data_types may be empty or omit types. A type the Attestation Provider does not publish is reserved for the Relying Parties it authorises (Metadata §3).
    • Clarified If locale selection fails for ad-hoc metadata, the entry is not compatible (Metadata §5.4).
    • Clarified The Wallet may refuse issuance if locale selection fails for the returned metadata (Metadata §4).
    • Clarified The Annex examples list Payment as an empty object. The examples of dynamic rendering and of ad-hoc metadata use an issuer-defined transfer type, urn:paso:sca:com.example.bank:transfer:1 (Metadata Annex A).
    • Clarified Display metadata for SD-JWT VC credentials, previously in the SD-JWT VC and SVG module, is now here: integrity-verified Type Metadata may be used for display, in the priority order of OpenID4VCI §12.2.4 (Metadata §9).

    Verify Module

    • Breaking The ingestion endpoint is a proposal; a payment scheme or rulebook may define another forwarding mechanism. The body is always a signed JWT (typ paso-proof-package+jwt, sender's chain in x5c), optionally nested in a JWE (cty JWT, baseline ECDH-ES with P-256 and A256GCM). The plain application/json body is removed. The sender may be the Relying Party or a party forwarding on its behalf. 401 means the signature, typ or chain failed (Verify §4).
    • Breaking The rendering mode follows from the type. Where the rulebook has a Static Presentation section, the Authorizing Party checks that the entry carries no ad-hoc metadata and that display_locale is one of the rulebook's language tags; otherwise it checks display_locale against the metadata. It always checks metadata_integrity, and verifies ad-hoc metadata: the client is authorised, the type is unpublished, and the object conforms. For types used only with ad-hoc metadata, it checks the payload against that metadata. The amr check is removed (Verify §3).
    • Breaking The vp_token must contain exactly one PaSO presentation. The matched entry is the PaSO-targeted entry whose credential_ids contain the presentation's credential query and whose hash equals transaction_data_hash. The Authorizing Party does not require it to be the first-match entry. The hash algorithm must be sha-256 or the one the rulebook names (Verify §3).

    Risk Signals Module

    • New For a type supplied by ad-hoc metadata, the risk members come from the metadata object (Risk Signals §4.1).
    • Clarified When verifying, the Authorizing Party applies the risk signal profiles, enumerations and encryption requirements of the rulebook, as in draft-2, even where the Wallet does not implement the rulebook (Risk Signals §4.1, §7.2).
    • Clarified A Wallet applies rulebook risk sources only where it implements the rulebook, and otherwise the signed credential metadata (Risk Signals §4.1, §7.2).
    • Clarified Without an integrity-verified encryption key, the entry is not compatible with the credential (Risk Signals §7.3).
    • Clarified The caution against combining amr with encryption (former §7.8) is removed (Risk Signals §7).

    Risk Signal Registry

    • Clarified The amr signal no longer has to cover two categories of authentication elements in a PSD2 context, and an ecosystem that requires SCA is no longer obliged to publish a risk signal profile that requires it. SCA rests on holder binding (Registry, Core §4.2, §6.1).

    Log Module

    • New Replay of a statically rendered presentation reproduces the static presentation of the Wallet version recorded in wallet_instance_version, in the language reported in display_locale (Log §5).
    • Clarified Resolved resources no longer include SVG templates; they are the resources fetched for display, such as remote images (Log §3).

    Payment rulebook

    • Breaking Payment is always rendered statically. A Wallet that does not implement this rulebook cannot process Payment entries. Attestation Providers list Payment as an empty object, without claims or ui_labels. The payload contains exactly the claims of §1; the permission to add internal claims is removed (Payment §1, §3).
    • New Static Presentation section: amount and payee.name are shown on the same screen as the affirmative action, payee.logo may be shown, and the other claims are not shown. The strings are defined in English (fallback), German and French, without a security hint. The examples show static renderings in English and French. References move to §4 (Payment §3).

    Default risk profile

    • Breaking The profile includes urn:paso:risk:global:amr:1, so it lists eight required signals, each with a max_age of 600 seconds (Default).

    Removed

    • The Generic rulebook (urn:paso:sca:global:generic:*). Generic use cases use ad-hoc metadata.
    • The Mandate rulebook (urn:paso:sca:global:mandate:*).
    • The SD-JWT VC and SVG module. Its display-metadata rules moved to Metadata §9; SVG images are no longer supported.
    • The value types mini_markdown and template:*, and the display_type parameter.
    • The issuer-signed ad-hoc metadata JWT (adhoc-transaction-metadata+jwt).
